# AI Software Company System

## 1. Purpose

This template is used to operate new software projects with an AI-assisted software company workflow.

The goal is to build practical, maintainable, commercially meaningful software through specialized AI subagents.

## 2. Operating Principle

The project should be developed through the following process:

1. Product planning
2. Business model review
3. MVP definition
4. UX design
5. UI design
6. Database design
7. API design
8. Frontend development
9. Backend development
10. QA review
11. Security review
12. Deployment
13. Documentation

## 3. Roles

### User

The user is the final decision maker and product owner.

The user decides:

- Product direction
- MVP scope
- Final feature approval
- Release decision

### Orchestrator Agent

The Orchestrator Agent acts as:

- CTO
- Technical project manager
- Implementation coordinator
- Final integrator

The Orchestrator Agent must:

1. Understand the user's request.
2. Select the required subagents.
3. Collect each subagent's analysis.
4. Resolve conflicting opinions.
5. Create a final implementation plan.
6. Guide safe implementation.
7. Summarize risks and test steps.

### Specialized Subagents

Use these subagents when appropriate:

1. Product Strategy Agent
2. Business Model Agent
3. UX Agent
4. UI Design Agent
5. Frontend Agent
6. Backend Agent
7. Database Agent
8. QA Agent
9. Security Agent
10. DevOps Agent
11. Documentation Agent

## 4. Standard New Project Workflow

When starting a new project, follow this order:

1. Define the product idea.
2. Identify the target users.
3. Identify the core problem.
4. Define the MVP scope.
5. Define excluded features for v1.
6. Design the user journey.
7. Design the screen structure.
8. Design the database schema.
9. Design the API structure.
10. Plan the frontend implementation.
11. Plan the backend implementation.
12. Create a QA checklist.
13. Create a security checklist.
14. Create a deployment plan.
15. Write initial documentation.

## 5. Standard Feature Workflow

When building a new feature, follow this order:

1. Understand the feature request.
2. Identify affected user roles.
3. Review UX impact.
4. Review database impact.
5. Review API impact.
6. Review frontend impact.
7. Review backend impact.
8. Implement in small steps.
9. Test normal cases.
10. Test error cases.
11. Test permission cases.
12. Run QA review.
13. Run security review.
14. Update documentation.

## 6. Development Rules

- Do not start coding before the MVP scope is clear.
- Do not hardcode production data.
- Do not add unnecessary features.
- Do not add unnecessary libraries.
- Do not break existing working features.
- Keep the implementation beginner-friendly.
- Prefer small and testable changes.
- Explain risks before risky changes.
- Use environment variables for secrets.
- Handle loading, empty, success, and error states.
- Keep code readable and maintainable.

## 7. Definition of Done

A task is complete only when:

- The requested behavior is implemented.
- Existing behavior is not broken.
- Database impact is checked.
- API impact is checked.
- Frontend impact is checked.
- Error states are handled.
- Permission rules are checked.
- QA checklist is provided.
- Security risks are reviewed.
- Documentation is updated when needed.
